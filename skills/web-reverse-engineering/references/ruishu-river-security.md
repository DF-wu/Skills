# RiverSecurity / Botgate Reverse Engineering Special

RiverSecurity is one of the strongest dynamic protections on the Chinese internet, and the only system that requires "per-site independent reproduction". It does not rely on fingerprint judgment, but on **dynamic transformation**: the same protection logic differs on every delivery, so static signatures cannot be reused.

## Identification: first confirm whether the target is RiverSecurity

| Signal | Value | Description |
|---|---|---|
| Status code of the first cookieless request | `202` | generations 3, 4 |
| Status code of the first cookieless request | `412` | generation 5 and later |
| Response body characteristics | inline self-executing script + `<meta>` referencing external JS | of the form `c.FxJzG50F.dfe1675.js` |
| Cookie name | `FSSBBIl1UgzbN7N80S` / `FSSBBIl1UgzbN7N80T` | the two digits are the HTTP default port |
| Cookie name | `FSSBBIl1UgzbN7N443T` | `443` = HTTPS default port |
| Cookie name (generation 5 non-standard) | `vsKWUwn3HsfIO` / `WvY7XhIMu0fGT` | generation 5 no longer carries a port number |
| URL suffix parameter | `MmEwMD=4xxxxx` | generation 4 |
| URL suffix parameter | `bX3Xf9nD=5xxxxx` | generation 5 |

**Naming pattern**: `80` = HTTP default port, `443` = HTTPS default port. **The first digit of the cookie value is the RiverSecurity generation**.

**Two-stage flow**: the first request returns 202/412 → request a JS file separately → re-request the page carrying the JS-generated cookie → 200.

## Generation Differences

| Generation | Entry characteristics | Status code | Special points |
|---|---|---|---|
| generation 3 | `_$aW = _$c6_$l6();` | 202 | `_$c6` is actually `eval`, `_$l6()` is actually `call` |
| generation 4 | `ret = _$DG.call(_$6a, _$YK);` | 202 | **has a "generate fake cookie" step** |
| generation 5 | `ret = _$Yg.call(_$kc, _$mH);` / `_$ap = _$j5.call(_$_T, _$gp);` | 412 | no fake cookie step; cookie name carries no port |
| generation 6 | same variants as above | 412 | cookie is 173 digits long; derived from a 128-element array |

## Generation 6 Internal Structure (verifiable points)

- The final cookie is derived from a **128-element array**
- Of these, a 4-element array is generated by `_$Zb` as "random numbers from 0–255"
- The `_$hM` method uses a **256-element array** `_$yx._$4y` (this value can be fixed directly)
- Timestamp processing yields 4 values of the form `[1695610803, 1695611070, 394, -901278768]`, converted to a 16-element array and then bitwise XORed
- The core code resides in a **VM**, loaded by the external JS referenced from the `meta` of the 202/412 response page and activated by `eval`
- `$_ts` is a dynamic value and must be replaced after dynamic matching via regex or AST

## Two Routes

### Route A: environment simulation (bu-huanjing) (mainstream, low maintenance cost)

Construct a browser environment in Node sufficient to fool RiverSecurity detection, then run the site's VM code directly to produce the cookie.

Recommended stack: [`pysunday/sdenv`](https://github.com/pysunday/sdenv) (BSD-3-Clause, npm `sdenv`, Node ≥ 20.19.5, depends on `node-gyp`). Its core is `sdenv-jsdom` — a jsdom fork modified against RiverSecurity jsdom detection points. The author states: **with a fixed random seed plus some `sdenv-extend` plugins, the cookie generated by RiverSecurity VMP inside sdenv can match the browser**.

Companion projects by the same author:

| Project | Role |
|---|---|
| [`sdenv-jsdom`](https://github.com/pysunday/sdenv-jsdom) | purpose-built jsdom (forked with detection points modified) |
| [`sdenv-extend`](https://github.com/pysunday/sdenv-extend) | environment extension shared by Node and the browser |
| [`rs-reverse`](https://github.com/pysunday/rs-reverse) | RiverSecurity VMP pure algorithm reversal |

Similar public environment-simulation projects: `NodeSandbox`, `qxVm`, `boda_jsEnv`, `catvm`. The one that directly corresponds to "RiverSecurity + cookie consistency" is the sdenv series.

**Note**: the sdenv author states it was developed mainly for RiverSecurity VMP scenarios, with no guarantee of stable operation against other anti-bot products.

### Route B: pure algorithm reversal (high cost, no environment dependency)

[`pysunday/rs-reverse`](https://github.com/pysunday/rs-reverse) provides four subcommands:

```bash
# 1. Generate dynamic code: pass text containing $_ts.nsd and $_ts.cd, or give a URL directly
npx rs-reverse makecode
npx rs-reverse makecode -u https://target/path

# 2. Generate cookie (internally runs makecode first, then the reversal algorithm)
npx rs-reverse makecookie
node main.js makecookie -j ./path/to/main.js -f ./path/to/ts.json

# 3. Two-step request version (the first request carries the cookie into the second request)
npx rs-reverse makecode-high -u https://target/path

# 4. For debugging/demo: evaluate an expression directly
npx rs-reverse exec -c 'gv.cp2'
npx rs-reverse exec -c 'ascii2string(gv.keys)'
```

Key details:
- `-j` specifies the outer VM code file, `-f` specifies the `ts.json` config file
- If the target site has an **additional debugger version** and `basearr` is not adapted, confirm that the config pointed to by `-f` contains a `hasDebug` entry; if it is absent, add it manually or generate it automatically with `makecode`
- `makecode-high` must not be run consecutively, or it triggers a risk-control error
- Pure algorithm reversal requires following control-flow numbers (e.g. control flows 742/744/772) step by step

## Detection Points and Countermeasure Points

RiverSecurity generation 6 has moved from "breadth detection" to "depth verification" — paying more attention to **inter-property relationships** and **runtime behavior characteristics** (including strengthened property descriptor detection). Merely filling in the breadth of `window`/`document`/`navigator`/`screen` is no longer enough.

| Detection point | Behavior | Countermeasure |
|---|---|---|
| Automation framework | infinite loop inside the `l` function: `while (window["_phantom"] || window["__phantomas"]) {}` | set it to `undefined` during environment simulation; or use an sdenv-class framework |
| Property descriptors | detects whether getter/setter are native implementations | preserve native descriptor characteristics when using `Object.defineProperty` |
| Property relationships | cross-object validation (e.g. a plausible combination of `screen.width` and `devicePixelRatio`) | use environment snapshots collected from a real browser rather than hardcoding item by item |
| Fingerprint validation | cookie length correlates with fingerprint values such as canvas in `window.localStorage` | **a short cookie can pass the page, but data query endpoints validate the fingerprint** — the fingerprint must be self-consistent |
| Running Selenium/Playwright directly | community reports "it simply cannot be bypassed; everything is detected" | do not count on browser automation to bypass it directly |

## Key Difficulties (Realistic Assessment)

1. The code runs inside a VM + `eval`, so key logic cannot be found by static search
2. **Each site's algorithm is independent; there is no universal script** — the community consensus is "one script per site"
3. Control-flow numbering plus a dynamic `$_ts` makes pure algorithm reversal extremely expensive to maintain
4. Fast version iteration (generations 4→5→6, with non-standard versions also present)

**Vendor claim note**: a RiverSecurity R&D director once said "there are 2^32 algorithms in total, each with 2^24 variants, combined with 2^128 key combinations". This is a **company-side claim with no independent third-party reproduction, and it is unverified**. Do not use it as a technical specification.
